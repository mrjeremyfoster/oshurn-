# Oshurn Scale Blueprint

## Product principle

**Simple on the surface. Massive underneath.**

Oshurn uses familiar financial concepts and presents them through high-quality software. The goal is not to make finance complicated; it is to make understanding finance easier through technology.

## Product layers

1. **Financial foundation** — budgeting, saving, debt, goals, net worth, financial wellness and literacy.
2. **Connected workspace** — one place where tools, learning, goals, history and signals reinforce each other.
3. **Knowledge system** — searchable explanations, lessons, definitions and learning paths.
4. **Oshurn Intelligence** — educational AI that explains concepts and routes users to relevant tools and knowledge without presenting personalized regulated advice.
5. **Extensions** — focused utilities that expand the platform while sharing the same design system and data principles.
6. **Platform infrastructure** — reusable components, state contracts, privacy/security readiness, analytics and content infrastructure.

## How to make Oshurn feel enormous

- Build depth into a small number of core workflows instead of adding disconnected pages.
- Make every major tool reusable from multiple entry points.
- Preserve one visual language across public pages and authenticated software.
- Give users a clear home, but let the underlying system contain many specialized capabilities.
- Show relationships between tools: snapshot → metric → signal → goal → learning → next action.
- Use progressive disclosure so advanced capability appears when useful rather than crowding the interface.
- Treat content as structured product data so lessons, definitions and tools can connect.
- Design mobile first and scale the same system to larger screens.

## Quality gates

Every meaningful feature should answer yes to most of these:

- Does it solve a real user problem?
- Does it connect to an existing Oshurn capability?
- Is the calculation transparent and testable?
- Is the experience accessible and responsive?
- Does it preserve the education/software boundary?
- Can the component be reused elsewhere?
- Does it make Oshurn more useful rather than merely more decorative?

## Regulatory boundary

The core product is financial education, organization, calculations and software. Regulated financial services should remain clearly separated and should only be introduced later through deliberate compliance design, licensing, disclosures, supervision and appropriate workflows.

## North-star experience

A user should be able to arrive with a basic financial question, learn the concept, use a tool, save a goal, understand a resulting signal, revisit the information later and continue learning — all without the interface ever feeling crowded.
